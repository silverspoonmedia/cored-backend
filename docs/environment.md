# Environment configuration

How Monolith manages `.env` files across local, staging, and production.

## How it works

Laravel loads **one** `.env` file at boot. It does not merge `.env.local` + `.env.production` automatically (unlike some Node.js frameworks).

```
Committed (in git)                    Gitignored (per machine)
─────────────────────                 ──────────────────────────
.env.example          master catalog  .env              (active — Laravel reads this)
.env.local.example    local template  .env.profile      (active profile name)
.env.staging.example  staging         .env.local        (saved local snapshot)
.env.production.example production    .env.staging      (saved staging snapshot)
                                      .env.production   (saved production snapshot)
```

| File | Purpose |
|------|---------|
| `.env.example` | **Master catalog** — every variable with block comments. Do not copy directly; use it when adding or removing keys, then sync the profile templates. |
| `.env.local.example` | Local development defaults (debug on, polling notifications, `MAIL_MAILER=log`, database cache/queue). |
| `.env.staging.example` | Pre-production mirror: production-like security, playground **still enabled** (`APP_ENV !== production`). |
| `.env.production.example` | Hardened production defaults; playground routes disabled. |
| `.env` | **Active** environment file Laravel loads at runtime. Never commit. |
| `.env.profile` | One-line marker (`local`, `staging`, or `production`) for the active profile. Never commit. |
| `.env.local` / `.env.staging` / `.env.production` | **Saved snapshots** per profile on your machine. Never commit. |

## Quick start (local)

```bash
composer install
php artisan env:install local
```

This copies `.env.local.example` → `.env`, seeds `.env.local`, sets `.env.profile`, and generates `APP_KEY` and `JWT_SECRET` when empty.

Overwrite an existing `.env`:

```bash
php artisan env:install local --force
```

Then set at least:

| Variable | Notes |
|----------|--------|
| `APP_URL` | Base URL (e.g. `http://monolith.test` on Laragon) |
| `DB_*` | MySQL connection (`DB_CONNECTION=mysql` by default) |
| `MAIL_*` | Optional locally (`MAIL_MAILER=log` writes to log) |
| `PUSHER_*` / `APP_NOTIFICATION_TYPE` | Optional locally (bell uses polling by default) |
| `HCAPTCHA_*` | Disabled locally (`HCAPTCHA_ENABLED=false`) |

```bash
php artisan migrate
php artisan db:seed
npm install && npm run build
```

Or use the Composer shortcut (skips if `.env` already exists):

```bash
composer run setup
php artisan db:seed
```

## Application encryption keys

Every profile template includes two adjacent lines in the Application block:

```env
APP_KEY=""
APP_PREVIOUS_KEYS=""
```

| Variable | Role |
|----------|------|
| `APP_KEY` | Active Laravel encryption key (sessions, cookies, `Crypt` facade). Generated by `env:install` or `key:generate`. |
| `APP_PREVIOUS_KEYS` | Comma-separated retired keys after rotation. Wired to `config/app.php` → `previous_keys` so data encrypted with an old key can still be decrypted. |

### Why `APP_PREVIOUS_KEYS` exists

Laravel's stock `key:generate` matches `APP_KEY` in `.env` using `config('app.key')` from the **already-booted** application. That breaks when:

- `.env` uses quoted values (`APP_KEY="base64:..."`) but config was loaded differently
- The file has `APP_KEY=""` while config still holds a previous key (common in tests and after `env:install`)

Monolith overrides `key:generate` via [`EnvironmentKeyWriter`](../app/Support/EnvironmentKeyWriter.php). It always reads/writes the file directly and uses the **`APP_PREVIOUS_KEYS` line as a stable anchor** on the line immediately after `APP_KEY`.

Legacy `.env` files missing `APP_PREVIOUS_KEYS` get the anchor inserted automatically on the next `key:generate` run.

### Rotating keys

```bash
php artisan key:generate --force
```

With `--force` and an existing `APP_KEY`:

1. The current key is appended to `APP_PREVIOUS_KEYS` (deduplicated)
2. A new `APP_KEY` is written

Fresh install or empty `APP_KEY` — only step 2 runs; `APP_PREVIOUS_KEYS` stays empty.

Show a key without writing:

```bash
php artisan key:generate --show
```

## Switching profiles (local dev)

Laravel only reads `.env` — it does not know about "local" vs "staging". Monolith keeps **separate saved snapshots** so you can switch without losing per-profile values.

| Command | Purpose |
|---------|---------|
| `php artisan env:install {profile}` | **Fresh** setup from `.env.{profile}.example` — resets that profile's snapshot |
| `php artisan env:switch {profile}` | **Switch** active `.env` — saves current profile, loads target snapshot |
| `php artisan env:switch` | Show active profile |
| `php artisan env:switch --list` | Table of profiles with snapshot status |

### Typical workflow

```bash
# First-time setup
php artisan env:install local
# Edit .env — set DB_*, APP_URL, secrets, etc.

# Switch to staging (first visit bootstraps from .env.staging.example)
php artisan env:switch staging
# Edit .env for staging-specific values

# Switch back — local values restored from .env.local
php artisan env:switch local

# After switching
php artisan config:clear
```

### What happens on switch

1. Current `.env` is saved to `.env.{current}` (profile from `.env.profile`, or inferred from `APP_ENV`)
2. If `.env.{target}` does not exist yet, it is bootstrapped from `.env.{target}.example` (secrets generated)
3. `.env.{target}` is copied to `.env`
4. `.env.profile` is updated

Switching to the **same** profile is a no-op (no data loss).

**Reset a profile** from template (destructive for that snapshot):

```bash
php artisan env:install staging --force
```

### Migration from `.env`-only setups

If you already have a `.env` but no snapshots, the first `env:switch` infers the current profile from `APP_ENV` and saves it before activating the target.

`env:switch` is intended for **local development**. Production servers typically keep a single `.env` (or platform-injected env vars).

## Staging and production

On the target server:

```bash
php artisan env:install staging     # or production
```

Fill in real values for:

- `APP_URL`
- `DB_*`
- `MAIL_*` (SMTP)
- `REDIS_*` (staging/production templates use `redis` for cache and queue)
- `PUSHER_*` and `CUSTOM_S3_*` when using realtime notifications and file uploads
- `HCAPTCHA_*` (enabled in staging/production templates)

After deploy:

```bash
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan migrate --force
npm run build
```

Production platforms (Laravel Forge, Vapor, Kubernetes, CI/CD) can inject env vars instead of a `.env` file. The variable names stay the same.

## Profile differences

| Variable | local | staging | production |
|----------|-------|---------|------------|
| `APP_ENV` | `local` | `staging` | `production` |
| `APP_DEBUG` | `true` | `false` | `false` |
| `LOG_LEVEL` | `debug` | `info` | `warning` |
| `SESSION_SECURE_COOKIE` | `false` | `true` | `true` |
| `SESSION_ENCRYPT` | `false` | `true` | `true` |
| `HCAPTCHA_ENABLED` | `false` | `true` | `true` |
| `MAIL_MAILER` | `log` | `smtp` | `smtp` |
| `CACHE_STORE` / `QUEUE_CONNECTION` | `database` | `redis` | `redis` |
| `APP_NOTIFICATION_TYPE` | `polling` | `realtime` | `realtime` |
| Playground routes | enabled | enabled | **disabled** |

## Production checklist

- `APP_ENV=production` and `APP_DEBUG=false`
- `SESSION_SECURE_COOKIE=true` and `SESSION_ENCRYPT=true`
- `JWT_SECRET` generated (`env:install` does this on first run)
- `HCAPTCHA_ENABLED=true` with valid keys
- Verify playground is off: `APP_ENV=production php artisan route:list --path=api/playground` (no routes)
- See also [README Security checklist](../README.md#security)

## Keeping templates in sync

When you add or remove an environment variable:

1. Update `.env.example` (master catalog + block comment).
2. Add the same key to `.env.local.example`, `.env.staging.example`, and `.env.production.example` with profile-appropriate defaults.
3. Run tests — `EnvProfileSyncTest` fails if keys drift between templates.

## Testing environment

PHPUnit sets `APP_ENV=testing` and overrides drivers in `phpunit.xml`. No `.env.testing.example` is needed.
