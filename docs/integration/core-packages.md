# Core domain packages

A **core domain** can ship as a Composer path package under `packages/{slug}/` instead of living in `app/Domain/{Domain}/`. The point is downstream reuse: a client project installs `silverspoonmedia/navigation` without forking this repo. Extraction moves **where** the code lives, never its contract — namespace `App\Domain\{Domain}\*`, route names, config keys, migration timestamps, and un-namespaced translation keys (`api/navigation.created`) are unchanged. **One package may carry more than one core domain.** A package is a *distribution unit*, not a taxonomy mirror: domains consumed together ship together. `silverspoonmedia/audit` bundles ActivityLog + ErrorLog; `silverspoonmedia/billing` bundles PaymentGateway + **Currency** + Service (one money surface — the vocabulary, the catalog priced in it, the invoice that collects for it); `silverspoonmedia/ai` bundles Inference + Ai, because a rate nobody can bill is not a price. Product domains stay in `app/Domain/{Product}/` and keep their `uninstall.json` contract ([architecture.md](../platform/architecture.md)).

## The kernel is a package too

`silverspoonmedia/platform` carries the code every package imports but no package owns: `App\Support\*`, the Identity hub (`App\Domain\Identity\*`), the HTTP glue (`App\Http\{Controllers,Requests,Resources,Middleware}`), `App\Repositories\*`, `App\Providers\{Encryption,Product,DomainAccess,Settings,Domain\Identity}ServiceProvider`, `App\Rules\*`, `App\Traits\*`, `App\Exceptions\*`. Namespaces are unchanged — extraction moved **where** the file lives, never the `use` line.

- **Every non-kernel package requires it.** `packages/{navigation,notification,audit,billing,ai}/composer.json` carry `"silverspoonmedia/platform": "^1.1"`; `DependencyDirectionTest::test_every_non_kernel_package_requires_the_platform_package()` fails on a package that imports kernel code without declaring it. `DependencyDirectionTest::test_kernel_reaches_a_package_only_through_a_kernel_contract()` holds the other direction with an **empty** burn-down list (there is no allowlist constant to grow), so a package that reaches back into the kernel except through a declared contract fails too.
- **The host requires a range, not `*`.** Root `composer.json` pins each path package with `"^1.1"`; `PackageManifestTest::test_root_requirement_is_a_caret_constraint()` fails on a wildcard (only the VCS dependency `silverspoonmedia/pdf-tools` is exempt, it is pinned to a commit hash). `test_locked_versions_match_package_manifests()` fails when `composer.lock` and `packages/{slug}/composer.json` disagree on a version, and `test_every_package_declares_the_kernel_at_its_own_minor()` fails when a sibling requires the kernel at a different minor than its own `version`. Bumps go through `-Bump` + `composer update silverspoonmedia/* --no-scripts` in the same commit; a manifest bump without the lock refresh is now a red gate, not a silent drift.
- **The host still wins.** Root `composer.json` re-declares `App\Support\`, `App\Http\`, `App\Repositories\`, `App\Domain\Identity\` over `app/`, which is how four product-coupled files stay in the host as overrides: `app/Support/Product/Services/{ProductAnalyticsService,ProductInsightService}.php` and `app/Support/ListActions/Builders/{HashBlocklistQueryRowActions,MicrostockCredentialQueryRowActions}.php`. `PackageOverrideTest` asserts an override file wins the PSR-4 race.
- **`helpers.php` ships once.** `src/Support/Settings/helpers.php` loads through the package's `autoload.files`; the root manifest must **not** list it again or every function is declared twice (fatal on boot).
- **Migrations stay host-owned.** `users`, `password_reset_tokens`, `sessions`, `cache`, `jobs`, `permission_tables`, `system_settings`, `product_*` and `identity_oauth_accounts` live in `database/migrations/` — the package ships the models for a host-owned schema, and its tests build that schema through `App\Support\Testing\KernelSchema`. A host may re-run those migrations from the package by publishing them with `php artisan vendor:publish --tag=silverspoon-platform-migrations`.

## Invariants

1. **The host wins the PSR-4 race.** Root `composer.json` declares `"App\\Domain\\Navigation\\": "app/Domain/Navigation/"` explicitly, so the generated map is `[app/Domain/Navigation, vendor/silverspoonmedia/navigation/src]`. Dropping that line makes every host override dead code, silently — `PackageOverrideTest` asserts it. A bundled package declares **one prefix per domain** it carries.
2. **The kernel never imports a package.** It declares the contract it needs — `PresentedTreeEpoch` for navigation, `DecryptionAuditRecorder` for the decrypt choke point, `ExceptionRecorder` for `bootstrap/app.php`'s `reportable()` — and the package binds it; a host without the package still boots because every call sits behind `app()->bound()`. A core package may import `App\Support\*` and the Identity hub, never a product domain.
3. **The package owns its wiring.** `extra.laravel.providers` auto-discovers the provider, which alone calls `mergeConfigFrom`, `loadMigrationsFrom`, `translator->getLoader()->addPath(__DIR__.'/../resources/lang')`, binds contracts, registers listeners and commands. `bootstrap/*` mentioning the package again is a defect. A bundled package has **one** provider for all its domains.
   Removing a package means removing its **registry entries** too: with the package gone but `config/domains.php` still naming its `routes`, the kernel boots (`php artisan about` works, no package class is referenced) and route registration fails on a missing controller. Clear `bootstrap/cache/{packages,services}.php` first — a stale `packages.php` still names the auto-discovered provider and fails provider load before the real cause is visible.
4. **Paths come from the registry.** `domainPath()`, `providerPath()`, `apiRoutePath()`, `testsPath()` read `config/domains.php` and fall back to `app/Domain/*`; no caller hardcodes either shape. Bundled domains at the same `path` still name their **own** `routes` file.
5. **A package pins its `version`.** A path repository otherwise infers `dev-{branch}` and `composer update` fails against `minimum-stability: stable` on any feature branch.
6. **Bundling never merges namespaces.** A package with two domains keeps `App\Domain\A\*` and `App\Domain\B\*` as separate PSR-4 prefixes and separate test prefixes; a shared `App\Domain\Audit\*` would have changed every import, which extraction must never do.

## Anatomy

`composer.json` (version, PSR-4 for `src` + `database/{factories,seeders}` + `tests`, `extra.laravel.providers`, `require-dev` = `orchestra/testbench` + `phpunit/phpunit`, `scripts.test`) · `src/` · `routes/{domain}.php` — one per domain, no prefix/name, the host applies them (a single-domain package may use `routes/api.php`) · `config/{slug}.php` · `database/{migrations,seeders,factories}` (original timestamps, `App\Domain\{Domain}\Database\*` namespaces) · `resources/lang/{locale}/**` · `tests/` (`App\Domain\{Domain}\Tests`) · `phpunit.xml.dist` (one suite over the declared `tests/` directories).

A package with a **web route** (OAuth callback, payment return) adds a `web` key to its registry entry and a file named `routes/web-{what}.php` (`packages/billing/routes/web-ipaymu-return.php`, `packages/platform/routes/web-identity-oauth-callback.php`); `routes/web.php` loops `packageWebRoutePaths()` instead of a literal `require`, so the `web` middleware group still wraps it. Non-PHP package data (routing YAML) lives in `resources/` and is addressed from the host config (`config/payment-routing.php` → `packages/billing/resources/routing/price.yaml`).

Host side: `"type": "path"` repository over `packages/*`, a `require` per package, the explicit PSR-4 prefix, and a `Package:{slug}` suite per package in `phpunit.xml` — the full run covers every suite, `--testsuite=Package:billing` runs one tree. `PackageTestSuiteTest` keeps file and tree in agreement (tests nobody wired contribute zero assertions, silently) and refuses a directory wired twice.

A package's tests run **standalone**: every test extends `App\Support\Testing\PackageTestCase` (Orchestra Testbench), which boots the kernel providers plus the package's own provider, builds the kernel schema through `App\Support\Testing\KernelSchema` and the package's own migrations, and mounts routes straight off each booted provider's package: `routes/*.php` under the `/api/v1` group and `routes/web-*.php` under `web`. In this checkout the registry (`config/domains.php`) decides; a consumer install adds no registry, so the package's own `routes/` directory is the source. Nothing comes from `bootstrap/app.php`, `database/migrations` or `tests/**`, so a consumer who clones a tag can run the same tests. `PackageTestSuiteTest::test_every_package_test_runs_under_the_standalone_base()` and `DependencyDirectionTest::test_no_package_test_imports_a_host_only_fixture()` keep it that way.

The honest limit: a test that needs a **host-assembled extra** route (the kernel's `packages/platform/routes/kernel-{settings,product-activations,domain-access,batch,broadcasting}.php`), a host **fixture** (the audit package's subscriber, the published `lang/{locale}.json` packs) or a **product** row (Microstock AI credits, Archivd quota) stays in `tests/Domain/Core/{Domain}/` under the host `Tests\TestCase`. The kernel's own surface ships whole: `packages/platform/routes/identity.php` and `routes/web-identity-oauth-callback.php` are registry route files, and the seven Identity feature tests (`AuthFlow`, `HcaptchaAuth`, `LoginThrottle`, `UserManagement`, `Lookup`, `ProfileConnectionsApi`, `DiscordOAuthCallbackWeb`) run in the standalone suite against those files.

`scripts/run-standalone-package-suite.php` (`composer test:standalone`, the `standalone-packages` CI job) copies each package to a temp directory, resolves siblings from source and runs `composer test` (`@php vendor/bin/phpunit` against the package's own `phpunit.xml.dist`); the same job runs `scripts/run-consumer-scaffold-check.php` against `client-scaffold/` (including its own `tests/`). Locale guards scan `lang/` **plus** `packages/*/resources/lang` (`locale_scan_lang_roots()`); `LocaleParityTest` reads both trees.

A packaged domain's config usually moves with it (`packages/notification/config/notification.php`, `packages/audit/config/errorlog.php`). The exception is a **published vendor config the host owns**: `config/activitylog.php` stays in the host because it is Spatie's file, merged last, with `sensitive_properties.*` in it — the same package can therefore own one config and leave another in place. The kernel ships `spa-routes.php`, `localization.php`, `services.php` and `hcaptcha.php` (merged shallow by `KernelServiceProvider` / `IdentityServiceProvider`, host wins) because Navigation, Identity and the Discord callback read them on a kernel-only install; `packages/billing/config/services.php` carries the `frankfurter` FX block for the same reason, merged by `BillingServiceProvider`. A product name inside `packages/platform/config/*` is drift the manifest reference scan reports.

That split only holds while the kernel side stays a **subset** of the host side, and `KernelConfigParityTest` proves it: `spa-routes.menu`/`deny` kernel entries must exist in the host list (a product domain may add entries, the kernel may not invent one), `localization.php` must be the same document in both places, every top-level `services` block the kernel ships must exist on the host, and `frankfurter` resolves from the billing merge while the host carries no copy of it. The other half of an override hook is the PSR-4 race: the root re-declares `App\Support\`, `App\Http\`, `App\Repositories\`, `App\Traits\`, `App\Rules\`, `App\Exceptions\` and `Database\{Factories,Seeders}\` ahead of the package entry, and `PackageOverrideTest::test_kernel_override_prefixes_resolve_host_first()` writes one probe class per prefix to prove the host copy still wins. Invariants: [architecture.mdc](../../.cursor/rules/architecture.mdc).

A product `uninstall.json` that cited a moved file records the package path (`packages/navigation/database/seeders/MenuSeeder.php`, `packages/billing/tests/Service/Unit/Services/ServiceEntitlementServiceTest.php`) — removing the product never removes the package.

## Seams and distribution rules

A core package may import `App\Support\*` and the Identity hub — never a product domain ([architecture.mdc](../../.cursor/rules/architecture.mdc)). When the packaged domains are *about* products, the coupling moves into kernel contracts the product implements; a **fork** needs the same seams to work with no product at all, so every one is a registry of class strings or a config key the product publishes from its own provider. Both tables — contract, kernel owner, package use, product side, and the empty state — are in [reference-package-seams.md](reference-package-seams.md). The only config-key seam is `config('ai.usage_event_resource')`: a JSON resource is a class instantiated per row, so a kernel interface would only add a hop. An EMPTY registry is a legal state (`PackageOverrideTest::test_kernel_boots_without_the_audit_package()`), and class strings rather than instances keep an Octane worker from pinning a product service.

The monolith stays the **only source**; each package also has a read-only mirror in the `silverspoonmedia` org. Publish, version and tag rules — one-way mirror, tag-not-branch release, `version` only here, `tests/` never shipped, `KernelServiceProvider` consumer-registered, no git subtree — are [reference-package-seams.md](reference-package-seams.md#distribution-rules).
