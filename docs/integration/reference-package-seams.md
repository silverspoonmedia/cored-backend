# Reference — package seams and the distribution rules

Deep dive for [core-packages.md](core-packages.md). Two halves: the seams a **bundled package** reads from a product that still lives in this repo, and the invariants that keep `packages/*` publishable. The fork-facing table (what a downstream product registers, and the empty state) is [client-project.md](client-project.md).

## Seams a bundled package needs

A core package may import `App\Support\*` and the Identity hub — never a product domain ([architecture.mdc](../../.cursor/rules/architecture.mdc)). When the packaged domains are *about* products, the coupling moves into kernel contracts the product implements:

| Contract | Kernel owner | Package use | Product side |
|---|---|---|---|
| `Support\Billing\Contracts\FulfillmentHandler` + `FulfillmentContext` | `Support\Billing\FulfillmentRegistry` (singleton) | `ServiceFulfillmentService` / `ServiceEntitlementLifecycleService` call `forTarget($target)`, never a product class | `Archivd\Support\Billing\ArchivdFulfillmentHandler`, `Microstock\Support\Billing\MicrostockFulfillmentHandler` register in their provider behind `app()->bound()` |
| `Support\Billing\Contracts\TierObserver` | same registry (`registerTierObserver`) | reports derived tier moves (`paid`/`grace`/`free`) | `ArchivdTierObserver` moves the product analytics tier |
| `Support\ActivityLog\{SubjectAliasRegistrar,SubjectLabelRegistrar}` | `packages/audit` binds `SubjectTypeResolver` / `SubjectLabelRegistry` | the trail maps `?subject=menu` and renders `subject_label` without naming a sibling package | `NavigationServiceProvider` registers `menu` → `Menu::class` and `MenuSubjectLabelPresenter`, both behind `app()->bound()` |
| `Support\Notifications\Contracts\NotificationDispatcher` | `packages/notification` binds the adapter | emits a **string** type (`service.entitlement.grace`) | adapter maps the string to `NotificationType` |
| `Support\Broadcasting\Contracts\ChannelRegistrar` | `routes/channels.php` loops it behind `app()->bound()` | registers `payments.invoice.{id}` / `payments.routing` / `payments.admin` / `services.catalog` | host keeps `settings.currencies`, `logs.*`, RBAC |
| `Support\Encryption\Contracts\LegacyColumnMigrator` | `Support\Encryption\EncryptionMigrationRegistry` | registers the `invoices.gateway_request_payload` / `gateway_response_payload` migrator | — (keeps `EncryptionMigrateP0Command` free of `Invoice`) |
| `Support\Ai\Contracts\AiUsageLedger` | bound by the product provider | `InferenceUsageAnalyticsService` reads the event model, its eager-load relations and USD formatting | `Microstock\Support\Ai\MicrostockAiUsageLedger` |
| `Support\Ai\AiUsageConsolidatorRegistry` + `Contracts\AiUsageConsolidator` | `AppServiceProvider` singleton | `InferenceCatalogService::syncProviderRates()` consolidates the ledger registered **under the provider slug** | `Microstock\Support\Ai\MicrostockAiUsageConsolidator` registers with `config('microstock.ai.inference_provider_slug')` |
| `config('ai.usage_event_resource')` | config key, published by the product provider | the dashboard controller renders the product's row class | `Microstock\Support\Ai\MicrostockAdminUsageEventResource` |

The AI seam is the one place a **config key** stands in for a contract: a JSON resource is a class instantiated per row, and a kernel interface returning a class-string would only add a hop. `AiServiceProvider` ships `'usage_event_resource' => ''`; with no product installed the admin usage dashboard returns an empty page instead of a package import. An EMPTY registry is a legal state — with no product installed the package runs the same code and every hook is a no-op (`PackageOverrideTest::test_kernel_boots_without_the_audit_package()`), and a registry of **class strings** rather than instances keeps an Octane worker from pinning a product service.

## Distribution rules

The monolith stays the **only source**. `packages/{slug}/` is edited here, required here through the `path` repository, and installed here as a junction — nothing about day-to-day work changes because a mirror exists.

Each package also has a **read-only mirror repo** in the `silverspoonmedia` org — `github.com/silverspoonmedia/{platform,navigation,notification,audit,billing,ai}` — so a consumer can `composer require` it without access to this repo. The consumer workflow itself — template, core-only registry, `vendor/` paths, override hooks, the config split — is [client-project.md](client-project.md).

1. **Never push to a mirror by hand.** A mirror is a one-way derivative produced by `scripts/publish-packages.ps1`; a manual commit there is lost on the next publish.
2. **Release is a tag, not a branch.** Publish with `scripts/publish-packages.ps1 -Version vX.Y.Z -Bump` from `main`; `-Bump` writes that version into every selected `packages/{slug}/composer.json` and commits it, then the script creates the repo if missing, runs `git subtree split --prefix=packages/{slug}`, pushes the split to the mirror's `main`, strips the `version` field, and tags that commit. `scripts/verify-mirrors.ps1 -Tag vX.Y.Z` then compares every mirror's `main` with a local subtree split and its newest tag with the pinned version — non-zero when anything drifted. Re-running for a published tag replays the strip commit on the new `main` and keeps the tag on its original commit, so a consumer that already locked that tag still resolves it.

    **The `v1.1` line.** `v1.1.0` published the fork seams: `SettingContributor` + `MenuContributor` (a product registers its settings groups and menu nodes from its own provider, so a product-free host boots with an empty catalog and no product group), `storage.upload_proxy.*` (a product publishes its upload proxy into the kernel's `storage` group instead of the kernel reading the product's config), `ai.consumers` / `ai.ledger_fk_targets` (the AI package names no product), and the SPA `FeatureModule` registry. Every manifest and the scaffold require `^1.1`; `PackageManifestTest` keeps the siblings on the kernel's own minor, and `ConsumerScaffoldTest::test_the_scaffold_requires_the_same_caret_line_as_the_root()` keeps the template from lagging a release.
3. **`version` exists only in the monolith.** A path repository needs it ([invariant 5](core-packages.md#invariants)); a tagged VCS repository must not have it, or every tag reports `1.0.0` and `^1.0` cannot tell releases apart.
4. **`tests/` never ships in the tag — but it runs.** Each package carries a `.gitattributes` with `export-ignore` for `tests/` and `.github/`, so the tarball is source only. The source repo keeps `tests/` with its `phpunit.xml.dist`, so a clone of the mirror runs `composer install && composer test`; `composer test:standalone` proves that path for all six packages. **A consumer installs by VCS**, because the mirrors are private: `{"type": "vcs", "url": "https://github.com/silverspoonmedia/billing.git"}` plus `"silverspoonmedia/billing": "^1.1"` — Composer needs a token that can read the org, and `composer update` in a throwaway manifest locks the tag (`"version": "v1.1.0"` with the mirror's commit as `reference`). `scripts/run-vcs-consumer-check.php` is the proof: it copies `client-scaffold`, installs from the six mirrors with a GitHub token, and asserts the lock, the core-only registry, the mounted URIs and one booted request. The consumer-side recipe is [client-project.md](client-project.md).
5. **A mirror is not a PR target.** Two-way contribution would need a different model (the package repo as source of truth); this repo deliberately keeps the source, so a change starts here.
6. **`KernelServiceProvider` is registered by the consumer, not auto-discovered.** It owns what the host's `AppServiceProvider` owns here (four seam registries, `EloquentCrudRepositoryInterface`, `CorsService`), the five kernel config merges, and the two commands that edit nothing durable — `domain:list` and `encryption:flush-decrypted-cache` (registered in `boot()` from `packages/platform/src/Console/Commands/`; `domain:make` / `domain:remove` rewrite host trees and stay host-only) — all behind `! $this->app->bound(...)` guards, so one provider answers per install. Since tag `v1.0.5` a consumer runs both from `vendor/`; `KernelConsoleCommandsTest` asserts that wiring inside the package. It stays out of `extra.laravel.providers`: auto-discovery would boot it here too and discard a resolved registry. `ConsumerScaffoldTest` asserts the scaffold lists it in `bootstrap/providers.php`.
7. **No git subtree.** A consumer never vendored this repo as `core/`: `update-core.sh`, `push-core.sh` and `client-subtree.md` are deleted, and `tests/Unit/Documentation/CoreScriptTest.php` fails if they return. A subtree snapshot could not be upgraded; the packages are the upgrade path. **Adding one:** `git mv` each piece (never copy: history follows), rewrite only the `Database\*` and `Tests\*` namespaces, write `composer.json` (version, `require-dev` with Testbench, `scripts.test`, PSR-4 for `tests/`), add `phpunit.xml.dist`, fold the old provider body into the package provider, add the registry entry + `require` + PSR-4 prefix, then delete the host copies and `bootstrap/*` references. Verify with `composer update silverspoonmedia/*`, `composer dump-autoload`, `php artisan domain:list`, `php artisan route:list --path=api/v1`, `php artisan test --testsuite=Package:{slug}`, `php scripts/run-standalone-package-suite.php {slug}`, and the locale parity scripts — the route count must equal the pre-move baseline. Windows: `"symlink": true` produces a junction and works here; if it ever fails, set `"symlink": false` and re-run `composer update silverspoonmedia/*` after every change under `packages/`.
